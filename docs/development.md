## Owner approvals

Decision `61e1d6c6cf8d` (task `d162a81b9411`). Until then every owner decision was a quote the manager signed; the owner key had never signed (retrospective `16cbeff051ea`).

- **Gated actions need an approval the owner signed** as `owner`: model runs (they spend money), publishing, access or protection changes, and the rest of the owner's go above. The owner runs `scripts/owner-approve <id> "<what they approve>"` in a terminal. `<id>` is what's approved: a task, a run's claim, or, for a merge, the current `pr` claim itself. It shows that contribution, asks the owner to type `approve`, and contributes a claim tagged `approval`, signed as `owner`, that `supports` it. Then it prints the approval's id, which the owner gives the manager. It refuses to run as anyone but `owner` or without a terminal, and it never reads or prints a key. Its writes need a team token for `owner`.
- **The `owner` team token is the owner's go.** Only the manager issues it (`scripts/team-server token owner`, which restarts the team server), and only with the owner's go, recorded as an `approval`; keeping one counts the same. Without it, `scripts/bk` refuses every write `--as owner`, which stops an agent signing as owner by mistake. With it, because keys are shared, any agent's `scripts/bk claim … --as owner` is written and confirmed, with no prompt.
- **The manager may sign on the owner's delegation** (decision `49cb2097aeeb`), one approval at a time. It first asks the owner for that specific approval and gets an explicit yes in chat. Then it runs `scripts/owner-approve <id> "<what>" --delegated "<the owner's yes, quoted>" --as owner`, which asks nothing. The approval is tagged `approval` and `delegated`, and its statement says the manager signed it on the owner's delegation, quoting the yes, with the date. Without `--delegated`, the statement says the owner ran it. There's no standing grant: each run signs one approval, and a quote any approval ever held is refused, retracted or superseded ones too. A delegated approval rests on the manager's account of the owner's yes: nothing checks the quote, so it carries the same weight as a manager-signed quote, only better labelled. `scripts/merge --owner-approval` accepts either kind and says which it found.
- **The manager checks the signature** before a gated action: `scripts/bk show <approval>` must show author `owner`. For a PR whose class needs the owner's go, run `scripts/merge … --owner-approval`. Its `owner` check needs a current owner-signed approval that `supports` the current `pr` claim itself. An approval of a task, another PR or an earlier head doesn't count, so each new head needs a new approval.
- **Quotes still count for everything else.** The manager may still record owner decisions it hears in chat as quotes, tagged `decision` ("Owner, <date>: '…'"), for choices that aren't gated.
- **This records intent, not proof.** In v0 every agent on this machine can read every identity's key, `owner`'s included (a key the team server holds too: it's a file of the same user). An owner-signed approval the owner ran says the owner meant it, as long as no agent signs as `owner` without leave. Only the manager may, with `--delegated`, and that approval is only as good as the manager's word. Every other agent that needs an approval asks the manager (process section 3).

## Harness

- **Where worktrees live:** builders' in `~/.t3/worktrees/bracken/<branch>`; delegated children's in `~/.t3/worktrees/bracken/t3-<id>`, on a `t3/<name>` branch or detached. T3 doesn't remove either, so the manager does (process section 6, Worktrees). Threads the owner opens on this repo also get `t3-<id>` worktrees, so match each one to a finished child or builder through `t3_worktree_list` and the thread's status before removing it by hand. `scripts/cleanup` doesn't match them: it removes a `t3-<id>` worktree only when it's clean, idle 2 hours and no process has it open, and `lsof` shows a live thread's process with its working directory there. Scratch worktrees and other scratch go under the team's scratch root, `$TMPDIR/bracken-scratch/<task id>`.
- **Briefs for reviewers and other children** say: make any checkout (a clean copy, a mutation copy, a verify run) under `$TMPDIR/bracken-scratch/<task id>`, and remove it with `git worktree remove` on every exit, passed, failed or stopped, before reporting.
- **`scripts/cleanup`** (owner process `11f1ac552f26`) frees what finished work left: `git worktree remove` for clean, unused `t3-<id>` worktrees and checkouts under `$TMPDIR` idle 2 hours, builders' worktrees whose branch's changes are all in `origin/main`, and the scratch root's entries idle 2 hours. A builder's branch counts as merged when merging it into `origin/main` changes nothing, or when its own patch since the merge base reverse-applies to some commit on main's first-parent line, as after GitHub's squash merge with later commits on main (task `268f5a72c4f2`). While `origin` still has the branch, only the worktree's `target/` goes (directly, not with `cargo clean`, which also clears a shared build dir). Once `origin` has deleted it, as `scripts/merge` has it do on merging, the whole worktree goes with `git worktree remove`, and its local branch with `git branch -D`, if nothing but `target/` and bracken's `.bracken/cache/` is ignored in it and its tip is the head a current `pr` claim names for it (`PR #<n> <branch> @ <sha>: …`); both are printed. A branch whose tip moved since its claimed head, or that no `pr` claim names, stays, saying so (finding `e2741e2be8cc`: a local commit after the squash merge that undoes part of the branch drops out of its patch). `git fetch --prune` deletes a remote-tracking ref's reflog with it, so the claim is what records the last pushed tip. A builder's worktree still has to be clean, unused by any process and idle 2 hours. Messaging that builder's thread afterwards makes T3 recreate the worktree (gotcha `a6751fa1`). A builder's worktree that stays for any other reason (unmerged, dirty, young, on no branch, commits only it holds), except one in use or out of bounds, still loses its `target/` when no process has a file open in the worktree and nothing in `target/` changed for the target idle time: 3 hours by default, `--target-idle <hours>` or `CLEANUP_TARGET_IDLE_HOURS` (task `cb478ca0bd41`, the owner asking on 2026-10-31 for less disk use). Waiting on review, worktrees kept 5 to 11 GB each, and with sccache a rebuild is cheap. Only `target/` goes, removed directly, never a source. A symlinked `target/`, or one resolving elsewhere, is never followed. Likewise, in a scratch entry it keeps (holding a checkout, or changed in the last 2 hours) but that no process has open, it removes each idle cargo target dir, one holding cargo's `CACHEDIR.TAG`, as `CARGO_TARGET_DIR` makes. Each such line starts `clean` and gives the size. It removes a target dir only where `lsof` runs, and with `--apply` it looks again just before: it renames the dir aside in its own directory, looks once more, and only then deletes it, putting it back if anything uses the worktree or entry (finding `176efeffc76f`). A copy renamed aside that a run couldn't finish with (`target.cleanup-<pid>`: the put-back failed because a build had made a new `target/`, the `rm` failed, or the run was killed) goes on the same rule in a later run once no process with that pid runs, and doesn't make the worktree dirty meanwhile; `.gitignore` covers `/target.cleanup-*` (finding `88fc809d6a05`). Before removing a scratch entry or a worktree, `--apply` also looks again; a scratch entry is renamed aside and looked at once more, putting it back if anything uses it, and goes only where `lsof` runs. It sizes a worktree before that look, so the removal follows it at once (finding `075b4a4dbcfd`). An entry holding a `.keep` file (a file, not a symlink or directory) touched in the last 24 hours, and not later than now, stays whole (as does one whose `.keep` can't be dated: finding `df3b4dc4966f`), its cargo target dirs and any worktree inside it included: a builder whose scratch is only read for a while touches it (task `02acb1d6e7e0`). An entry left renamed aside as `<entry>.cleanup-<pid>` by a run that was stopped is put back under its name once that run is over, never cleared; if the name exists again, both stay, for the manager. A run stopped by INT, TERM or HUP puts back the entry it has aside (finding `910ae8ed0fe3`). What it judged before a slow step (`du`, `lsof`, the merge check, the Ground read) it checks again after the last look, just before the removal: a worktree whose HEAD, branch, files (`git status`, ignored ones too), scratch `.keep` or last use changed since it was judged clean stays, and a renamed-aside scratch entry that has come to hold a fresh `.keep`, a git checkout or a change in the last 2 hours, or a target dir changed in the time it had to be idle (the target idle time, or 2 hours for a merged worktree's), is put back (finding `497ffa3fdcdc`), as is a target dir whose scratch entry has come to hold a fresh `.keep` (finding `1efc75ddf0cb`). Inside a scratch entry it never goes into a `pg-*` directory or another repository's checkout, at any level (finding `2b3fe543e130`). A dry run by default, which changes nothing (no fetch either); `--apply` fetches `origin` and acts. Each line says what it does or why not, and it ends with the space freed and free, and how much of Docker's build cache could be reclaimed (`docker system df`, given 20 s). It never prunes Docker, which the owner's other projects share. It never touches a dirty worktree, `.bracken/`, `~/bracken-runs`, anything named `pg-*` (PineGrove's), other repos or anything outside those places; the "won't touch" lines are for the manager's weekly look. `scripts/merge` runs `cleanup --apply` after each merge (a failure never undoes the merge), and a daily T3 scheduled task will, once the manager adds it (approval `e31616fa27ec`). `scripts/verify-seq` warns below 50 GB free and refuses below 20 GB (`VERIFY_SEQ_WARN_GB`, `VERIFY_SEQ_MIN_GB`; `VERIFY_SEQ_MIN_GB=0` runs anyway).
- **No file deletion in Bash.** Claude Code asks a human to approve an `rm` it can't prove safe, even in full-access mode, and overnight that blocks the agent until the owner wakes. The owner's user-level hook `~/.claude/hooks/bracken-no-rm.py` refuses any Bash command running `rm` in this repo's checkouts and worktrees, with advice, so the agent carries on at once. Use `git worktree remove`, `git rm` or `trash <path>`, and leave `mktemp -d` directories in place. The hook is outside the repo: a new machine needs it installed in `~/.claude/settings.json` under `PreToolUse`, matcher `Bash|Monitor`.

## Builds

Rust build artifacts were filling the disk: about 10 GB per worktree's `target/`, across 9 to 10 worktrees. Three settings make builds smaller and share their work (owner decision `8ac9b0239d90`, task `23e73664dc45`). A shared `target/` isn't one of them, because cargo's lock on it would make the builders wait for each other.

- **No incremental compilation:** `.cargo/config.toml`, `[build] incremental = false`. Incremental state was about 5.5 of those 10 GB, and sccache can't cache an incremental compile. A one-line change rebuilds its crate whole, which costs seconds here.
- **Line tables only:** `[profile.dev] debug = "line-tables-only"` in the root `Cargo.toml`, which tests inherit. Panics and backtraces keep their files and line numbers, but a debugger sees no variables. For a debugging session, set `CARGO_PROFILE_DEV_DEBUG=true` for that build. Dependencies are still built at `opt-level = 2` (see the box's table below).
- **sccache:** `.cargo/config.toml`'s `build.rustc-wrapper` is `scripts/rustc-wrapper`.
  - Cargo resolves that path from the directory holding `.cargo/`, so each worktree runs its own copy, from any directory in it.
  - With `sccache` on `PATH` (installed here with `cargo install --locked sccache`, reference `58df550f1788`), every compile goes through one cache that all worktrees on this Mac share. It's capped at `SCCACHE_CACHE_SIZE`, which is 15G unless the environment sets it.
  - Without sccache, the wrapper runs rustc itself, so a machine without it builds as before.
  - Everything goes through it: every worktree, the manager's counted run, and `scripts/test-table --remote`'s box. The box has no sccache, so there it always runs rustc directly. A `RUSTC_WRAPPER` in the environment would replace it, so don't set one.
  - Clippy on the workspace's own crates skips the cache, so a lint is never answered from a cache made under other lint flags.
  - The server listens on a unix socket in `/tmp/bracken-sccache-<uid>`, which the wrapper creates at mode 0700, never on a TCP port that any local process could reach and have it run a program (finding `292898be0ce0`). If that directory is a symlink, someone else's, or any mode but 0700, the wrapper skips sccache and runs rustc directly.
  - The manager's counted runs never read the cache. `scripts/test-table` sets `SCCACHE_RECACHE=1`, so every compile of the Mac half of `--split`, and of a local table, runs afresh and refreshes its entry. A merge never rests on cache entries a branch's build wrote.

**What sccache sees.** sccache's client sends its environment to a long-lived server, which runs the compiler with it. So the wrapper gives sccache only what a compile needs:
- the names cargo sets for a compile (`CARGO_PKG_*`, `CARGO_BIN_EXE_*`, `CARGO_MANIFEST_*`, `CARGO_CRATE_NAME`, `CARGO_PRIMARY_PACKAGE`, `CARGO_CFG_*`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_MAKEFLAGS`, `DEP_*` and a few more, listed in the wrapper), even with `AUTH` or `TOKEN` in a name, as in `CARGO_PKG_AUTHORS` (finding `58223509a78e`);
- `RUSTC*`, `RUST_*` and `CLIPPY_*`, unless the name looks like a secret;
- `OUT_DIR` and the build-script variables;
- `PATH`, `HOME`, `TMPDIR`, the locale, and the C toolchain's variables;
- and `SCCACHE_*`.

Apart from the names cargo sets for a compile, it never passes a name containing `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL` or `AUTH`, or ending in `_KEY`, so a user's `CARGO_FORGE_TOKEN` or a registry token stays out (finding `289f76c488af`), and never one it doesn't list. It prints nothing and logs nothing: it drops `SCCACHE_LOG` and `SCCACHE_ERROR_LOG` too.

If a dependency's build script sets a variable for its crate's compile (`cargo:rustc-env=NAME=…`), that variable must be in the wrapper's `KEEP` list. Otherwise the crate fails to compile with "environment variable not defined". None of today's dependencies built on macOS or Linux sets one.

If sccache can't reach or start its server, as in a sandbox that denies its socket, sccache prints its error (`sccache: error: …`) and exits 2 before the compiler runs. The wrapper then runs the compiler itself, so the build goes on without the cache (finding `20a5ceea1005`). An error while reading the server's answer is ignored the same way (`SCCACHE_IGNORE_SERVER_IO_ERROR=1`). sccache 0.19 also exits 2 when a compile it ran itself was killed by a signal (a crash, the OOM killer), and then its last line on stdout ends with `sccache: Compile terminated by signal <n>` (the compiler's stdout may have begun that line, finding `19b295a1bb9a`): the wrapper, which copies sccache's stdout as it passes, passes that one on, never rerun (finding `ec492ce1a7d1`). A killed compile the server ran ends 254, its note last on stdout `sccache: Compiler killed by signal <n>`, also passed on. sccache's own fatal error also ends 254, with `sccache: encountered fatal error` on a line of its own on stderr, in place of the compile's output, as from a server started with a `TMPDIR` that has since been deleted, which then fails every compile on the machine with `Failed to create temp dir` (gotcha `fc6e6835ad88`). Code the compiler runs, such as a proc macro, can end a compile 254 too; with no such line, that's the compile's own exit, passed on and never rerun (finding `2d0978e6cdfd`). Only for sccache's fatal error does the wrapper say so in one line on stderr, stop that server so the next compile starts a fresh one, and run the compiler itself (task `f5849cee0423`). For that it copies stderr too, as it passes, through a fifo in the same private directory; without the copy of stdout or of stderr it passes every 254 on. Any other exit 2 is rerun once without sccache, as before: sccache's errors can't be sorted reliably into before and after the compile (one context, `failed to execute compile`, covers both, and the compiler's stderr shares the stream), so an error after a compile that had already run is also rerun, which costs only time. So is every exit 2 if the copy can't be made. The wrapper touches no file descriptor but stdout and stderr, so cargo's jobserver (`--jobserver-auth=3,5`) reaches sccache and the compiler as it is.

**When the server crashes.** A server that dies mid-build, killed (`kill -9`) or out of memory, fails the build in progress, though sccache says it's compiling locally instead (finding `5c32bca03ce6`). The reviewer saw `failed to build archive … memory map must have a non-zero length`, twice in two tries. The compile the dead server had started and sccache's local retry seem to collide on the same output. Rerun the same build: it succeeds, with a new server. A build failing just after such a crash, a counted run's included, is that, not a fault in the change. So stop the server with `--stop-server` (below), which no build notices, and never kill it.

**Talking to sccache.** Run it through the wrapper, `scripts/rustc-wrapper <sccache arguments>`, never as plain `sccache`. Any sccache command starts the server if it isn't running, and the server would then keep the shell's whole environment.
- `scripts/rustc-wrapper --show-stats`: hits, misses and the cache's size.
- `scripts/rustc-wrapper --zero-stats`: reset the counts.

**Clearing the cache.**
1. Stop the server: `scripts/rustc-wrapper --stop-server`.
2. Remove the cache directory: `trash ~/Library/Caches/Mozilla.sccache`. `--show-stats` prints its location as `Cache location`.

The next compile starts a new server with an empty cache. Clearing it changes no build's result, only its speed. A worktree's own `target/` still goes with `trash target`, or `scripts/cleanup`.

**How much it saved** (measured 2026-10-31 on this Mac, task `23e73664dc45`, before at main `b721d8e3` and after at this change):

| Measure | Before | After |
|---|---|---|
| A fresh worktree's `target/` after `cargo nextest run -P fast --workspace` | 2.52 GiB, 1.21 GiB of it incremental | 1.27 GiB, none incremental |
| Building every fast test binary (`--no-run --build-jobs 4`) in a fresh worktree, empty cache | 803 s | 354 s |
| The same in a second worktree, cache warm from the first | 803 s (no cache to share) | 131 s: 122 of 162 compiles from the cache |

- The cache held 206 MiB after both worktrees.
- Its misses are the workspace's own crates: their cache keys include the worktree's path, so each worktree compiles them once.
- The machine's load ran from about 45 to 250 during these builds, so the times are rough. The sizes aren't affected.
- A long-lived worktree's `target/` grew far past 2.5 GB before, because incremental state piles up with every build. Without it, a rebuild replaces what it rebuilds.

## The Pi prefix

A Pi run pins one install of Pi and the node that runs it, not the owner's: `scripts/pi-prefix <dir>` builds it (macOS on arm64). It unpacks nodejs.org's node at the version the script pins, checked against the sha256 in the script, then installs exactly `crates/experiment/pi/package-lock.json` with that node's own npm. npm runs with no install scripts, no npmrc and nothing of your environment. Build it under the scratch root, for example `$TMPDIR/bracken-scratch/<task id>/pi-prefix`; it's read-only once built, so remove it with `chmod -R u+w` first.

Two tests in `crates/experiment/tests/pi.rs` need it and are ignored otherwise: one runs its node under the Node sandbox profile, and one plays a whole Pi turn through the forwarding proxy to a stub provider, with a test CA made at test time. No model is called. Run them with `EXPERIMENT_PI_PREFIX=<dir> cargo nextest run -p bracken-experiment --test pi --run-ignored only`. The counted run doesn't build the prefix (answer `8064daa71ddf` (3)).

`bracken-experiment run --harness pi --pi-prefix <dir>` plays every turn with that prefix in place of `--claude`; `--pi-version` (1.4.0 by default) is the version the prefix must hold. Pi's provider is `--pi-provider anthropic` (the default), routed by the same `--settings` file, or `--pi-provider openrouter`, which goes to Pi's own OpenRouter URL with the key from the `openrouter` entry of a Pi `auth.json` given as `--pi-auth` (task `19228e53a342`). That entry may be a stored API key or Pi's OpenRouter login, whose `access` is a permanent API key that Pi sends the same way (decision `467e1c8dbc09`). Only the entry's type and key, or the login's `access` and `expires`, are read. A login that expires before the run's time cap plus 30 minutes is refused, with a request to log in to Pi again; it is never refreshed, and nothing writes the file. A key Pi would run or expand (`!…`, `$…`), or one with any character outside `A-Za-z0-9._-`, is refused (finding `b85965153a9b`). Either way the key reaches Pi only in the one environment entry it reads for that provider (`ANTHROPIC_AUTH_TOKEN` or `OPENROUTER_API_KEY`), and the forwarding proxy reaches only that host. `--pi-thinking` sets the thinking level, the plan's effort, which is medium unless given; pick one the model supports (DeepSeek V4.1 Flash has off, low, high and max). The options of the other harness or provider are refused. Pi's compaction is off, and a compaction beginning stops the run, since its summary call's tokens would escape the caps (finding `ac5a014447a1`). The first usage row and the plan's `harness` field record the harness: its pin, profile, declared entries, where a turn's result comes from, and whether a test CA was trusted (finding `695de67678dd`). A real run calls a model, so it needs the owner's go.

To upgrade Pi, change the version in `crates/experiment/pi/package.json`, run `scripts/pi-prefix --lock`, and review the new lockfile as a dependency change: a supply-chain check in security review (answer `cc34f6275877` (1)).

### `scripts/test-table --remote`

It tests HEAD, so commit first: it refuses a dirty tree, and needs `origin/main` (fetch it). It puts HEAD and `origin/main` in a git bundle, the only thing pushed, and runs one `boat run --no-env --push <bundle dir> --type default --timeout 2400`. In the box, it installs what the box lacks (below), clones the bundle with HEAD checked out and `origin/main` beside it, and runs the same, unchanged `scripts/test-table`, Ground guards included: the bundle is 5 MB and takes under a second, so the guards check the same commits as locally. The guards use the debug `bracken` the table just built (`BRACKEN_BIN`). With `-p <package> ...` the box runs only `cargo test --locked -p <package> ...` in place of the table, and the last line says it wasn't the whole table; a name that doesn't look like a cargo package name is refused before any box. It prints the box's output, then `test-table: box: exit N · time · type · cost`, and exits with the box's exit code (130 if interrupted).

The box is deleted on every way out. `boat run` deletes it when the command ends, fails or times out, and when it's interrupted (Ctrl-C). Once boat has printed the box's id (`bx_… ready`), `--remote` also checks `boat list --all` as it exits, for any reason, and deletes the box by id if it's listed in any state, or if boat can't list boxes at all; plain `boat list` shows only running boxes, and one left stopped, pending, stopping or in error keeps its data (gotcha `93bae3ba4156`). If the box is still listed after that, it says so with the command to delete it. A Ctrl-C before boat prints the id leaves the deletion to `boat run` alone: check `boat list --all`. `crates/bracken/tests/scripts/test_table.rs` tests this with a stub `boat` that lists like the real one: a failed run that leaves its box stopped and an interrupted one each leave no box.

### `scripts/test-table --split`: the manager's counted run

**How much it covers** (owner decision `464d3ccca45e`, answer `10cf8a5053a3`): the manager chooses, per merge, by risk, and the evidence's details say which mode it chose and why.
- **Full**, the whole table (`--split`, below): the default. It's required whenever `scripts/code-scope full` names a path the head changed since main:
  - `crates/manyroot`, the protocol crate;
  - the root `Cargo.toml` or `Cargo.lock`;
  - `docs/protocol.md`;
  - all of `crates/tree/src/` and `crates/tree/Cargo.toml`, which hold the Weave validity code the weave-v1 fixture pins, and `crates/tree/tests/weave_fixture.rs` and `crates/tree/tests/fixtures/` (findings `4320dbb473bb`, `be317d39449b`: a list of modules missed `lib.rs`, `check.rs` and the manifest, and would rot);
  - `.cargo/`, `rust-toolchain*` and any `build.rs` (finding `398c794c1707`), which change every build.

  A rename or deletion of one of these counts too. A Rust file changed only in comments doesn't, and names a doc's row, as `code-scope packages` gives it (task `0837da3df7a4`): `bracken-scope comment-only <base> <head> <file>` compares its tokens on both sides, doc comments counting as code, and calls a file that doesn't lex, or that a file includes as text (`include_str!`), code. Blank lines after an outer attribute count too. `code-scope` asks it twice, from the merge base to the head and from main's tip to the merged tree, and a conflict is code (finding `24e15486a4a4`). Such a head is never docs-only, since clippy reads plain comments (finding `c40ed7b8d3f8`): its light run includes both clippies.

  Also by the starting policy: a batch of several heads touching shared crates, a builder's evidence missing or not on the exact head, a recent flake in the touched area, a release or anything that deploys, and anything else the manager judges risky. Batches (`--batch`, `--speculative`) are always full for now.
- **Weave** (stage 2b step 1b, owner approval `e8fd45c83ba6`, decision `bbbf898cbcfe`): `ON=origin/main scripts/verify-seq --weave <pr claim>:<sha> ...`, only while the Weave gate is on (`scripts/weave-gate state`). It has line main's Weave checks (fmt, clippy, table in a box, mac here) run on main merged with the head, through `scripts/weave`, and records a pointer that `scripts/merge` counts as the whole table after checking it afresh (`scripts/weave-gate check`). The manager turns the gate on with a claim tagged `weave-gate` reading `Weave gate: on`, and off by superseding it with one reading `Weave gate: off`, as plan `cc496dcee0e3` section 6's stop conditions require. A head it can't count (a conflict, no Weave proposal named in its pr claim, a change to `scripts/test-table`, its template copy or `Cargo.lock`, a check not green) is named with the reason and needs git's counted run. Batches always take git's run. Light heads can take either: a Weave pass is the whole table.
- **Light**, `ON=origin/main scripts/verify-seq --light [--reason <why>] <pr claim>:<sha> ...`, one head at a time. Its scope is `scripts/code-scope packages`: the packages the files the head changed since main affect, never the builder's choice (findings `0095e19fcdb7`, `4825c59b07e9`). That's every package when `code-scope full` names a path, and otherwise what `bracken-scope packages` (`crates/scope`) prints for the changed paths, a Rust file changed only in comments counting as `README.md` (owner decision `73f2ba4c08e5`, task `de42fa5c776d`): guppy's determinator over the two commits' package graphs (`cargo metadata --offline --locked --filter-platform <host>` of each, unpacked in a throwaway directory), with the rules in `.config/determinator.toml` for paths outside the crates. `code-scope` builds bracken-scope from its own checkout, and the rules are compiled in, so `merge` judges by main's tool and rules, never the head's. `AGENTS.md`'s Tests table documents what it prints. For each head it first checks, and refuses, recording nothing and saying why, unless all of these hold:
  - the scope isn't empty (a change only to `rustfmt.toml` has none);
  - the pr claim's author recorded passes on that exact head of `cargo fmt --check`, both clippies, `cargo nextest run -P fast -p <packages>` and `scripts/test-table --remote -p <packages>`, each naming at least the scope's packages (`scripts/code-scope light-passes`; the fast pass may also carry `-j <n>`, `--no-fail-fast` and `--test-threads <n>` among its `-p` arguments, and nothing else, task `b1156a629af9`);

  Those passes are a precondition only (finding `94e07ed7dd6b`). It then runs `scripts/test-table --split -p <the scope>` on main merged with the head (`bk-evidence --on`, without `--reuse`). The box runs `scripts/test-table --light -p <the scope>`: fmt, both clippies, `cargo nextest run -p <packages>` (the slow tests too), `cargo test --doc` for those with a library, and the Ground guards. Its scope check refuses it unless `code-scope full` names nothing, its packages include every one `code-scope packages` gives, and the pr claim's author has the same five passes on the exact head (finding `013ac6db02d9`). Every counted run's details end with `test-table: counted run mode: <light|full>: <why>`, which verify-seq sets. For light, that's the scope and the builder's passes it checked. For full, it's what `code-scope full` named, if anything, then `--reason` or `the default`.

It writes a manager claim tagged `batch` naming main, that tree's key and the members, records the run on it, and on a pass gives each member a pass whose method names the batch, main, the key and the run. On a fail it bisects over prefixes and records a fail (method ending `pinned`) only on the member whose addition turned a passing prefix into a failing one; if main alone fails, the members get nothing. Main alone runs the whole table except the Ground guards, which compare a head with main and have nothing to compare when HEAD is `origin/main`; `test-table` says it skipped them (task `1e89b53c6a4a`). `merge` still runs the guards on every head it merges. `scripts/merge --batch <batch claim> ...` checks every member before merging any, merges them in the tested order, and compares each squash merge's tree key before and after its POST; if anything fails part way it stops and says which members merged, since main is then on a prefix nothing tested. The plain `merge <pr> <claim>` accepts a batch pass only when the head merged with main's tip has exactly the tested key, never a prefix.

**The speculative queue** (task `74fb85858e88`, proposal `b4ebad7274a6`, answer `c3e60ba8b879`): `ON=origin/main scripts/verify-seq --split [-j N] --speculative <pr claim>:<sha> ...` tests reviewed heads A1..An as a merge queue, in the order given. Every prefix, main plus A1..Ai, is an ordinary batch of i on the same main (a claim tagged `batch` and `speculative`), and up to `-j` of them run at once, each its own `--split` run. Once prefix i and every prefix before it have passed, each of its members gets the batch pass for it. So the plain `merge Ai <claim>` accepts Ai by the exact-key rule above once main is main plus A1..A(i-1), and `merge --batch <prefix i>` merges A1..Ai at once; the acceptance rule is unchanged. The first prefix f that fails runs once more (and main alone, if f is 1). A passing rerun counts as a pass of that tree, with a note on the prefix's claim naming the suspected flake. A second fail pins Af, as `--batch` does. The prefixes after it are stopped and dropped, and the members after Af are tested again without it on the same main; prefixes before f keep their passes. A member that changes only docs, or doesn't merge onto the members before it, is refused up front by name. It ends by listing what passed, in merge order, what was pinned and what wasn't verified. A pass or pin it can't write isn't reported as done, and it exits 1. In every mode, a PR whose worktree can't be made, or whose run records nothing, is named, and `verify-seq` exits 1.

**Which tests are macOS-only comes from the code.** Every test that needs macOS goes in a `mod macos_only`: today the sandbox tests in `crates/experiment/tests/agent.rs` (ignored on Linux) and the ACL tests in `crates/demo` (compiled only on macOS). So do the tests that need Docker, though they don't need macOS: the Python profile's and the grader's in `crates/experiment` run agent code in a container (decision `ac22cedd8fee`), and Docker Desktop is on this Mac. Where Docker isn't running, or isn't on macOS and hasn't the image pulled, as in the boxes, each prints why it skipped and passes; on this Mac an image not pulled fails them. On this Mac they need the pinned image pulled once: `docker pull` the image `crates/experiment/src/python.rs` names as `IMAGE`. The box also lists the tests Linux has and those it ignores, and the Mac lists its own. Each side lists them twice over (answer `92eacabfd720`): `cargo nextest list --run-ignored all` and `--run-ignored only` for the tests in test binaries, and `cargo test --doc -- --list` and `-- --list --ignored` for the doctests, which nextest doesn't run. A test that runs on the Mac but is missing or ignored on Linux, and isn't in a `macos_only` module, fails the run by name, so no new test can be skipped on both sides.

Stopping it (a Ctrl-C, or a failure on the Mac side) stops both parts. Each runs as a job with job control, in its own process group, with SIGINT not ignored as a plain background job's is (finding `87cfdf4680c7`). Each part gets SIGINT, which `boat run` takes as an interrupt and deletes the box; after 15 s, SIGTERM; then SIGKILL. Then `test-table` deletes the box by id if `boat list --all` still shows it. The tests on the Mac run under `timeout`, in a process group of its own that it signals whole at the limit, so a test whose child hangs ends with everything it started (finding `c7d17b82e315`); their part passes a SIGINT or SIGTERM on to `timeout` as SIGTERM (a background `timeout` ignores SIGINT), which signals that group, and if the tests were stopped or hit their limit, `test-table` sends the group SIGKILL as it exits, in case a test that ignores SIGTERM outlived them; never after they ended by themselves. This Mac's test lists run the same way, each bounded at 300 s. Under `verify-seq`, every run is such a job too: a Ctrl-C to `verify-seq` is passed to each running run as SIGINT and a SIGTERM as SIGTERM, so a `verify-seq` started with SIGINT ignored still stops on SIGTERM (note `c1468539ea94`). A speculative run whose job dies without finishing has its process group sent SIGINT as well, so the `bk-evidence`, `test-table` and box it left behind stop (task `1d950948aa3f`); `verify-seq` waits up to 60 s for them to end before it removes the run's worktree, and otherwise leaves it, saying so (finding `fa85e1368475`). Both scripts find their jobs with `jobs -p`, which holds a job from its fork, so a signal before its pid is saved still reaches it. `bk-evidence` records nothing for a run it interrupts, and `verify-seq` exits 130. The test-list commands in the box run under `pipefail` and end with a marker line; a failed or cut-short list fails the run, so it can't hide a test that is ignored only on Linux.

### Using boat by hand

| Task | Command |
|---|---|
| Run a command in a fresh box, then delete it | `boat run --no-env --push <dir> [--type small\|default] [--timeout <s>] -- <cmd>`. `--push` copies the git-tracked and unignored files under `<dir>` to `~/<dir name>` in the box, and the command runs there. It prints `bx_<id> ready`, the command's output, and `exit N · time · type · cost · bx_<id> deleted` |
| See your boxes | `boat list --all` (JSON). Plain `boat list` shows only running ones. It should be empty whenever you aren't running something |
| Delete a box | `boat delete --yes <bx_id>`. Without a terminal, `--yes` is required |
| What's left of the plan | `boat limits` |

The rules for every box:

- **Always `--no-env`**, and never `-e`/`--env`: no secret, token or credential goes into a box, GitHub credentials included. A box gets no `~/.bracken-team`, no `.bracken/identities/` and nothing gitignored. Push a bundle or a clean directory, not a checkout with untracked files in it.
- **Run it in the foreground**, and delete the box yourself if anything stops `boat run` from doing so (check `boat list --all`).
- **A plain `--push .` has no `.git`.** Anything that needs git history (the Ground guards, git mode, tests that expect to be in a checkout) needs the bundle route that `--remote` uses: `git bundle create <dir>/tree.bundle HEAD refs/remotes/origin/main`, then in the box `git init -q tree && cd tree && git fetch -q ../tree.bundle +HEAD:refs/heads/tested +refs/remotes/origin/main:refs/remotes/origin/main && git checkout -q tested`.

### What a box has, and what tests need installed

A box is Ubuntu 24.04 (x86_64) with Rust 1.97 (cargo, clippy, rustfmt), cc, git 2.43, `timeout`, python3, `sudo` and `apt-get`. The test table also needs:

| Needed by | What | Install in the box |
|---|---|---|
| The Ground guards, tests run in a checkout | `git` and a clone with history | The history comes from the bundle (above) |
| The experiment's git-mode tests | a git newer than Ubuntu's 2.43, which neither traces the programs it starts (`trace: start_command:`) nor fsck-checks a fetched bundle, so the hub there accepted a malformed commit | `sudo add-apt-repository -y ppa:git-core/ppa && sudo apt-get install -y -qq git` (2.56 in October 2026; the tests need 2.46, `MIN_GIT`). test-table tries the PPA four times, 10, 30 and 90 s apart, and falls back to the image's git only if it's 2.46 or later, failing setup otherwise |
| `scripts/team-server token` and its test | `b3sum` | `apt-get install -y -qq b3sum` (or with `sudo`) |
| `scripts/cleanup`'s target removal and its tests | `lsof` | `apt-get install -y -qq lsof` (or with `sudo`) |
| The table's tests | cargo-nextest 0.9.150 (decision `4bf44934cb67` (4)) | Its pinned `x86_64-unknown-linux-gnu` release tarball, downloaded with `curl` and checked against the sha256 in `scripts/test-table` before it's unpacked; a mismatch stops the box |

`--remote` installs the PPA's git, `b3sum`, `lsof` and the pinned cargo-nextest in every box, quietly unless that fails: then it prints the failing command, its exit and its output, and stops; anything a future test needs goes in its inner script too, and in this table. On Linux, the experiment's sandboxed tests are skipped with a printed reason (`needs macOS sandbox-exec`): `sandbox-exec` exists only on macOS, and they still run there. The workspace builds dependencies at `opt-level = 2` even in debug (`Cargo.toml`), which made the demo's adversary tests three times faster; without it they alone took 13 minutes in a box.

## Remotes
